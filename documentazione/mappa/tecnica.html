2aIl nucleo: lo strato HTTP (novembre 2026)

Il portale aveva già quasi tutto il dominio in src/: mancava lo strato HTTP, e ogni pagina ripeteva a mano il controllo dei permessi, il token e l'escape. Il nucleo è quello strato, in 10 classi che non nominano il portale, e si aggiunge una pagina alla volta: gli indirizzi di sempre restano dove sono.

ClasseChe cosa fa
Richiestametodo, percorso, parametri e corpo della richiesta, letti una volta sola; Richiesta::finta() per le prove
Rispostal'unico punto che stampa: html(), contenuto(), json(), rimando(), negata(), vuota(), erroreServer()
Vista e DatiVistai modelli in viste/: $d->campo esce già escapato, $d->grezzo() solo se lo chiedi, nome mancante = eccezione
Rotta e Rottela tabella degli indirizzi: percorso, classe della pagina, titolo, file guscio. Rinunciare al token CSRF richiede un motivo scritto di almeno 30 caratteri
Nucleol'ordine fisso: accesso, token su ogni POST, poi la pagina. Un'eccezione diventa 500 con il messaggio generico e il dettaglio solo nei log
Paginal'interfaccia di una pagina: __invoke(Richiesta $r): Risposta, dipendenze nel costruttore
ControlloAccesso, ProtezioneCsrf, Avvisile tre interfacce con cui il nucleo chiede al portale chi può entrare, se il token è valido e che messaggi mostrare

Una pagina nuova: cinque mosse, una quarantina di righe

  1. Una riga in src/Portale/Instradamento/Rotte.php: new Rotta('percorso', PaginaX::class, 'Titolo', 'file.php'). Il percorso è il file di oggi senza .php, perché i due layout usano link relativi.
  2. Il guscio file.php, tre righe: config.php, functions.php, Nucleo::serviFile(__FILE__).
  3. La classe in src/Portale/Pagine/: final class PaginaX implements Pagina, dipendenze nel costruttore, __invoke. Niente echo, exit, $_GET, globali.
  4. Il modello in viste/: comincia con la guardia e scrive <?php echo $d->campo; ?>, già escapato.
  5. La prova con Richiesta::finta() (modello: tests/Integration/Portale/PaginaContattiTest.php).
Perché nessun indirizzo muore. I QR dei badge e delle aule, i link nelle email e nei PDF già firmati puntano a file .php: quei file restano, ridotti a gusci di tre righe. Cancellando nucleo.php e la regola 3b del .htaccess il portale risponde come prima: lo prova strumenti/prove/apache_nucleo.sh con Apache vero, confrontando ogni indirizzo con e senza nucleo.
Limiti noti (scritti in documentazione/nucleo.md per non riscoprirli): un indirizzo pulito sotto admin/ non arriva al nucleo, perché la regola 0 del .htaccess chiude lo scudo del pannello con [L]; ogni rotta ha oggi anche il suo file guscio; Vista ha tre proprietà statiche (layout, avvisi, radice) che andrebbero riviste su un server a processo persistente; gli avvisi si consumano solo quando un layout li mostra, così un rimando non li perde.

3Il ciclo di una richiesta

Quattro file di bootstrap, sempre nello stesso ordine. Cron e prove caricano solo functions.php.

  1. config.php: apre la sessione con cookie Secure, HttpOnly, SameSite=Lax; imposta gli header di sicurezza (HSTS, CSP, X-Frame-Options…); legge .env; apre $conn (mysqli).
  2. functions.php: include inc/*.php in ordine fisso, carica l'autoload PSR-4 (src/autoload.php), avvia il container (App::avvia($conn)) e chiama assicura_schema().
  3. middleware.php (solo pagine protette): sync_sso_user($conn) ricollega l'utente dalla sessione SSO; se manca, reindirizza a saml_login.php?redirect=…; poi espone $u_id, $u_ruolo, $is_full_admin, $user_info.
  4. admin/admin_header.php (pannello): autentica, calcola i permessi ($puo_fsl, $puo_didattica_tutto, $is_full_admin…), disegna menu e barra superiore.

Una pagina tipica (schema)

<?php
require_once 'middleware.php';                          // login + $user_info
$serv = \App\Core\App::get(\App\Didattica\ServizioPratiche::class);   // dal container

if ($_SERVER['REQUEST_METHOD'] === 'POST') {            // azioni in cima
    csrf_verify($_POST['csrf_token'] ?? '');
    $err = $serv->invia($_POST, $user_info);
    flash_set($err ?? 'Pratica inviata.', $err ? 'danger' : 'success');
    header('Location: pratiche.php'); exit;             // PRG: redirect + exit
}
$elenco = $serv->dello($user_info);                     // dati
require_once 'header.php'; ?>                           <!-- HTML sotto -->
Errori silenziosi. Le query che falliscono restituiscono false/[]/null (nessuna eccezione), come nel codice storico. Le classi nuove validano gli input e restituiscono messaggi d'errore come stringa (?string) o Esito.

4Routing, aree e layout

Non c'è un router PHP: contano il file system e un .htaccess. Le aree create da pannello non generano file.

  • URL puliti: /area_personale → area_personale.php se il file esiste; nel pannello admin/x → admin/x.php.
  • Regola «3b», il nucleo (novembre 2026): un indirizzo con una «/» che non è né un file né una cartella va a nucleo.php, che risponde con la pagina della rotta o con un 404 pulito senza aprire database e sessione. Restano fuori gli alberi di file (assets, uploads, cache, vendor, src, inc, tests, strumenti, database, backups, modelli_documenti): un'immagine che manca non deve avviare PHP. Gli indirizzi a un solo pezzo restano di area.php, e un indirizzo sotto admin/ non ci arriva, perché la regola 0 chiude prima con [L].
  • Aree dinamiche: una riga di pagine_eventi (slug, tipo_area: fsl, eventi, gruppi, calendario) è servita da area.php tramite regola di rewrite; gli slug che coincidono con file reali sono rifiutati.
  • Motore dei layout: master_template.php (≈ 250 righe, più i parziali in inc/area_pubblica/: un file per layout, scheda, modulo di iscrizione…) disegna la pagina di un'area con uno di otto layout:grid, list, advanced_list, calendar, timeline, agenda, gruppi, progetti. Le aree di tipo calendario includono calendario_area.php.
  • Moduli del pannello: MODULI_PORTALE (inc/sezioni.php) elenca cinque moduli (orientamento, fsl, calendari, didattica, portale); PAGINE_MODULO assegna ogni pagina al suo modulo.
  • Pagine a schede: admin/didattica.php prepara i dati comuni e include didattica_<scheda>.php due volte, con $fase = 'azioni' e poi 'vista'.

8Database e migrazioni automatiche

Non esistono script SQL da lanciare dopo un aggiornamento: lo schema si adegua da solo alla prima richiesta.

  • Core\Schema\Definizioni: tabelle() (CREATE TABLE IF NOT EXISTS), colonne() (ALTER … ADD COLUMN se manca), tipi() (correzioni di tipo per database vecchi).
  • Core\Schema\Migrazioni::aggiorna(): se esiste cache/schema_v<VERSIONE>.ok non fa nulla; altrimenti crea tabelle e colonne, poi datiDiPartenza() (seed, migrazioni di dati) e scrive il marcatore. Oggi VERSIONE = 147.
  • Si alza VERSIONE ogni volta che si tocca Definizioni o i dati di partenza.
  • Le migrazioni di dati sono idempotenti con una guardia. Esempio: migraUffici() copia le 4 tabelle storiche negli uffici/uffici_persone unificati una sola volta (finché non esiste l'ufficio direzione), preservando gli id e introducendo op_id, il numero stabile con cui pratiche.assegnata_a identifica l'operatore.
  • Il marcatore è condiviso tra database diversi sullo stesso codice: dopo un bump, su un secondo database va cancellato per rilanciare la migrazione.
// Definizioni::colonne() — aggiunge la colonna solo se manca
'verbali_accessi_log' => [
    'utente' => "ADD COLUMN utente VARCHAR(150) DEFAULT ''",
],
// Migrazioni::datiDiPartenza() — guardia per eseguirla una volta
$giaFatto = (int) $this->db->valore("SELECT COUNT(*) FROM uffici WHERE chiave = 'direzione'") > 0;
if (!$giaFatto) { /* copia uffici, persone, uffici di Ateneo e remap dei bandi */ }

Le macchine a stati dei processi principali. Gli stati sono costanti nel modulo; le transizioni stanno nei servizi, mai nelle pagine.

Pratica studente (didattica_moduli.iter_json)

L'iter è un array di passi. Ogni passo è un ufficio (id o chiave), un marcatore ("protocollo", "@cdl", "@segreteria") o un oggetto tipizzato:

["protocollo", "@cdl", "@segreteria"]                                  // iter semplice
[{"t":"persona","campo":"Relatore","gg":3},                       // firma/conferma di una persona del modulo
 {"t":"ufficio","u":"protocollo","gg":2,"pagamento":true},        // marche da bollo
 {"t":"ufficio","u":"@cdl","documento":true},                     // l'ufficio carica un documento
 {"t":"conferma","campo":"Docente"},                              // conferma docenti (senza firma digitale)
 {"t":"direttore","gg":4}]                                        // firma PAdES del Direttore

ServizioIter::definizione() normalizza i passi; ServizioFlussoConvalide::trasmettiAlPasso() sposta la pratica verificando le condizioni del passo; PromemoriaPratiche (cron) sollecita dopo gg giorni; FirmaPratica gestisce firme e link; la domanda in PDF/A è prodotta da DomandaPdfa e il testo del verbale da TestoVerbale.

Notifiche push (Web Push)

Scritte a mano con OpenSSL, senza Composer: CifraturaPush cifra il messaggio come vuole il browser (RFC 8291, aes128gcm; verificata contro il vettore di prova della RFC), ChiaviVapid firma la richiesta (ES256, RFC 8292) con le chiavi del .env (PUSH_VAPID_PUBLIC/PRIVATE/SUBJECT, create una volta con strumenti/genera_chiavi_push.php), InvioPush la spedisce con curl (ClienteHttp è un'interfaccia: nelle prove un finto). Un 404/410 elimina il recapito; dopo 5 errori di fila pure. Il sw.js riceve la notifica e al clic apre la chat giusta. Agli operatori arriva chi scrive e le prime parole; a chi chiede aiuto solo «hai una risposta», senza testo. Senza chiavi VAPID tutto resta com'è e valgono le email.

Didacticus: come decide

Motore confronta la domanda con le voci: normalizza (minuscole, senza accenti, parole vuote tolte), riduce ogni parola a una radice (senza vocale finale, al massimo 5 lettere) e calcola un punteggio 0–100 come somiglianza pesata (peso = rarità della parola tra le voci) con ogni domanda della voce; una parola chiave contenuta nella domanda porta la voce in alto in proporzione a quanta parte della domanda copre; l'argomento scelto dà un piccolo vantaggio. ServizioDidacticus traduce i punteggi: ≥ soglia (predefinita 60, regolabile 20–90) risposta con link, allegati e pulsanti; fino a 12 punti sotto la soglia suggerimenti; altrimenti nessuna (conta una domanda a vuoto: alla seconda di fila la chat passa a un operatore). Saluti, ringraziamenti e «voglio un operatore» sono riconosciuti a parte; una voce riservata a chi accede invita gli esterni ad accedere. Non genera testo e non chiama servizi esterni: dice solo quello che è scritto nelle voci.

Significato e modello linguistico (facoltativi)

Dopo il Motore, se le regole non sono sicure (punteggio sotto la soglia) o lo sono poco (sotto 75), ServizioSignificato confronta la domanda con i vettori delle voci: con somiglianza da 0,62 sceglie la voce (da 0,55 se deve correggere una scelta debole delle regole, che resta tra i «vedi anche»), da 0,50 propone «forse intendevi…». Le soglie si regolano con EMB_SOGLIA e EMB_SOGLIA_SUGGERISCI. Il testo mostrato è sempre quello della voce. Su 20 domande parafrasate trova la voce giusta in 15 casi contro 7 delle sole regole. Se resta incerto e LLM_URL è impostato, ModelloLinguistico può scrivere una risposta con le sole fonti; in prova (Llama 3.2 3B e 1B, Qwen, Phi-4-mini) sul server a 4 core senza GPU è troppo lento e a volte inventa, quindi resta spento.

Pratiche degli studenti (automatico)

   └─ FlussoPratica::avvia()                     // FlussoPraticaConProtocollo (decoratore)
        ├─ ServizioFlussoConvalide::avvia()      // PDF/A e primo ufficio dell'iter, come prima
        └─ ProtocolloAutomaticoPratica::dopoInvio($id)
              ├─ se il 1° passo è ITER_PERSONA / ITER_DIRETTORE / ITER_CONFERMA → aspetta (null)
              └─ altrimenti prendi(): protocollo vuoto + regola attiva → ProtocollaPraticaInTitulus::protocolla()
                    └─ registraProtocollo(): scrive numero e data; se il passo è un ufficio protocollo, passa avanti

ServizioFlussoConvalide::assegnaAUfficio()        // unico punto in cui una pratica arriva a un ufficio
   └─ se l'ufficio è di tipo «protocollo» → AlPassoProtocollo::raggiunto($id)
         └─ ProtocolloAlPasso → ProtocolloAutomaticoPratica::alPassoProtocollo($id)   // es. tesi dopo il relatore
  • Perché un'interfaccia (AlPassoProtocollo, implementata da ProtocolloAlPasso): il flusso non deve conoscere chi protocolla, e il protocollo automatico a sua volta registra il numero attraverso il flusso. ProtocolloAlPasso prende ProtocolloAutomaticoPratica da una Closure al momento dell'uso, altrimenti il container segnalerebbe una dipendenza circolare.
  • Tesi e moduli «approvazione prima»: ITER_TESI = [conferma(Relatore/trice), 'protocollo', '@cdl']. All'invio non si protocolla; quando il relatore conferma, assegnaAUfficio() porta la pratica al passo «protocollo» e scatta alPassoProtocollo(). Un iter che comincia con una conferma e non ha un passo protocollo (per esempio il Diploma Supplement: @cdl → direttore) non protocolla mai in automatico.
  • Dopo il protocollo modificabile() è falso: lo studente non può più cambiare la domanda.
  • Segnatura sul PDF: ServizioFlussoConvalide::registraProtocollo(), quando il numero è nuovo (automatico o scritto a mano), chiama DomandaPdfa::conSegnatura(). NNNNNNN del gg/mm/aaaa»; Infrastructure\Pdf\SegnaturaPdf::applica() aggiunge in testa alla prima pagina, a tutta larghezza, un'annotazione /Stamp (bordo e testo rossi) con un aggiornamento incrementale (nuova tabella xref o xref stream con /Prev): i byte originali non cambiano, quindi le firme PAdES restano valide (Acrobat può segnalare «modificato dopo la firma»). 15Sicurezza

Difesa in profondità, con le scelte che contano per un portale universitario.

Input e output

Prepared statement ovunque; output HTML sempre codificato; dati JS in json_encode; colori validati prima degli stili; QR letti mai aperti come link.

Sessione e CSRF

Cookie Secure/HttpOnly/SameSite=Lax; token CSRF su ogni POST; rigenera() all'accesso; dopo «Esci» nessun accesso SSO automatico.

Header

CSP in config.php, HSTS, X-Frame-Options, X-Content-Type-Options, Referrer-Policy; librerie con SRI SHA-384.

Permessi

Ogni azione verifica che evento, turno o pratica appartengano all'area o all'ufficio dell'utente; cron solo da CLI o con CRON_KEY.

Il no del nucleo

Nelle pagine servite dal nucleo accesso e token si controllano in un punto solo, prima di stampare: un token sbagliato dà 403 con 133 byte di testo e nient'altro, non mezza pagina. Il rifiuto per permesso mancante e quello per token sbagliato dicono la stessa frase, così non si distingue «non puoi» da «sessione scaduta». «Sei amministratore» si legge dal database, non dalla sessione: chi perde il ruolo lo perde subito.

«Entra come…»

La simulazione è di sola visione e scade da sola: la guardia (inc/simulazione_guardia.php) ferma i POST, gli indirizzi con una parola d'azione e gli script che scrivono anche su una GET semplice (self_checkin.php, che registrerebbe la presenza della persona che stai guardando).

File

uploads/, .env e cartelle interne negati dal web server; download solo da pagine che controllano il permesso.

Anti-abuso

Rate limit per IP, CAPTCHA interno, campo trappola; limite ai tentativi di password sui verbali.

Privacy

Nessuna connessione a terzi (font e librerie locali); IP anonimizzati nei registri dei verbali; conservazione e anonimizzazione automatiche.

Segreti

Solo nel .env (mai in git): DB, chiavi, Aruba, backup. Password SMTP cifrate nel database.

18Rilascio e operazioni

Il deploy è manuale e verificabile: si costruisce un pacchetto dall'ultimo commit e lo si estrae sul server.

# 1. sul PC: pacchetto con tutti i file committati (senza .env, uploads, cache, tests, strumenti, documentazione)
bash strumenti/crea_pacchetto.sh            # -> aggiornamento_completo.tgz  (+ SHA256SUMS_pacchetto.txt dentro)

# 2. sul server
cd /opt/lampp/htdocs/mydibest
tar -xzf aggiornamento_completo.tgz
sha256sum -c SHA256SUMS_pacchetto.txt | grep -v ": OK"     # non deve stampare nulla
find . -name '*.php' -not -path './uploads/*' -not -path './cache/*' -print0 | xargs -0 -n1 php -l | grep -v "^No syntax"

19Come aggiungere una funzione

La ricetta per un nuovo modulo o una nuova tabella, seguendo i pattern esistenti.

Due vie, non una. Per una pagina nuova conviene la via del nucleo (sezione 2a): una riga nella tabella delle rotte, un guscio di tre righe, una classe Pagina, un modello in viste/ e una prova con Richiesta::finta(). Quella che segue è la via di sempre, che resta valida per le 198 pagine non ancora convertite e per tutto quello che non è una pagina.
  1. Tabella: aggiungi il CREATE TABLE IF NOT EXISTS in Definizioni::tabelle() (o la colonna in colonne()) e alza Migrazioni::VERSIONE. I dati di partenza vanno in datiDiPartenza(), con una guardia di idempotenza.
  2. Repository in src/<Modulo>/: costruttore con Database, metodi con query preparate che restituiscono array.
  3. Servizio: regole e validazioni; restituisce ?string d'errore o i dati; riceve repository, notifiche e Orologio (mai new DateTime diretto, per testare).
  4. Notifiche: una classe che usa Mailer e Sito::urlBase() per i link.
  5. Pagina: require_once 'middleware.php', App::get(Servizio::class), azioni POST con csrf_verify + redirect, poi HTML. Se serve il pannello, usa admin_header.php e registra la pagina in PAGINE_MODULO e nel menu.
  6. Prove: un file in strumenti/prove/oop/<modulo>.php con prova(condizione, "descrizione") e, se serve, un test PHPUnit con DatabaseDiProva.
  7. Documenti: aggiorna README.md, il piano e la mappa dei file da caricare; costruisci il pacchetto e verifica con sha256sum -c.
Errori da evitare. Non scrivere HTML nei servizi; non leggere la sessione nelle classi (passa i dati); non fare ALTER fuori da Definizioni; non usare App::get() dentro src/; non dimenticare csrf_field() nei form.
